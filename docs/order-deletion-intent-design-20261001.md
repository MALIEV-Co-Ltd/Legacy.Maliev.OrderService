## Proposed durable record and response contract

Add Order DB table `OrderDeletionIntent`, no cross-database FK. Proposed fields: `OrderId` int primary key (one lifetime per immutable Order ID), `DeletionId` UUID unique, `RequestedAtUtc` timestamptz required, `StatusCleanupCompletedAtUtc` timestamptz nullable, `CompletedAtUtc` timestamptz nullable, `AttemptCount` int nonnegative, `NextAttemptAtUtc` timestamptz required. No token, actor headers, PII, exception text or serialized Order. Do not reuse existing nullable unique Order.OperationKey: it is a CREATE receipt and disappears with Order.

Insert intent and delete Order/files atomically in one Order transaction; history is untouched until that transaction durably commits. The stable DeletionId is generated once outside execution-strategy attempts. The record survives deletion and process restart. Immutable Order IDs must never be reused; detection of a live Order alongside an existing intent is a fail-closed conflict, not authorization to clean its history. This prohibition requires explicit acceptance and database/import tooling review.

Proposed outward compatibility: 204 only after both graphs are deleted and completion recorded; 404 only when no Order and no pending intent exists, or an already-completed deletion is replayed (preserve current missing-order replay). Pending intent retries resume cleanup and may return 204; unavailable cleanup/reconciliation returns generic 503, never misleading 404. Cancellation propagates; cancellation after Order commit leaves a recoverable durable pending intent, not restoration of a deleted Order. No claim of rollback across two databases. These outcomes need an explicit application result enum/controller mapping rather than silently overloading today's bool or leaking database exceptions. Parent approval required for the 503 extension.

## Shared fence and lock lifetime

All affected writers take an Order-database transaction-scoped advisory fence derived from a domain-separated Order ID, then re-read authoritative Order/intent. Exact key derivation is a reviewed compatibility contract, identical for every writer/worker. Lock order is always Order fence(s) -> Status transaction/row lock; never Status -> Order.

- Delete holds the Order fence while inserting the intent and deleting Order/files, through Order commit. After commit, the intent and absent Order prohibit any new status/history mutation. Cleanup then reacquires the same Order fence, verifies intent identity and absent Order, deletes Status history in its own transaction, commits, and marks completion in Order. Losing the fence at the first commit is safe only because every writer subsequently checks the durable intent, not merely a pre-transaction Order existence probe.
- Both TransitionAsync overloads must acquire the Order fence BEFORE any authoritative Order/current-history check and hold the Order transaction/fence across the Status commit and Accepted Order convergence. Fresh contexts on configured execution-strategy attempts are required; no reuse of tracked history after rollback/unknown commit. A transition that obtained the fence first completes before deletion; one that obtains it after intent commit denies with no appended event. Existing same-status replay/graph checks remain.
- UpdateHistoryAsync must discover the old Order ID without treating the discovery as authority, acquire old/new Order fences in ascending ID order, then lock/re-read the history row in Status and verify the old ID has not changed. Both referenced Orders must be live without an intent. Mismatch aborts the attempt; do not acquire additional locks in a different order mid-attempt.
- DeleteHistoryAsync also needs the associated Order fence and authoritative history re-read. Status definition/transition catalog writers do not create Order history, but their existing Status row/FK locks must be audited for reverse Order lock acquisition; they must never acquire Order after Status. Order/file writers must likewise reject an existing intent if they can target a deleted/reused ID.
- No claim that an ordinary HTTP history GET holds these fences today. Proposed reads of History/latest must check pending/completed intent and deny deleted Order visibility even while cleanup lags; choose 404 for absent Order rather than expose orphan history. Order cache reads must not return a tombstoned Order: authoritative intent/existence admission before cached value, or a separately approved durable cache-version design. Current swallowed cache removal failures and two-minute TTL cannot establish immediate invalidation.

Reversing the two DELETE statements alone leaves unknown commits, new history racing cleanup, process death and stale cache unresolved. A transaction-scoped advisory lock cannot span two Order commits: reacquisition plus authoritative intent is the required bridge, not an imaginary distributed transaction.

## Unknown commit, replay and worker guarantees

Use normally configured execution strategies and fresh context/transaction per attempt. On lost Order commit acknowledgement, independently read exact stable DeletionId/OrderId intent and absence of Order/files under the shared fence. Exact durable matching receipt resumes cleanup; absence permits a fresh attempt; contradictory state fails closed. Never infer success merely because an Order is missing.

Status cleanup is idempotent ExecuteDelete under its transaction. Lost acknowledgement can safely repeat only while the same intent is fenced and Order remains absent; all history writers honor the fence. Mark status completion only after confirmed cleanup/reconciled empty history. Lost Order completion acknowledgement is reconciled from the exact intent. Cancellation is never treated as permission to blindly retry; durable intent gives future request/worker recovery.

Bounded worker scans a partial index on pending `(NextAttemptAtUtc, OrderId)`; claims each intent under the same Order fence and row lock (`SKIP LOCKED` only for queue selection, not authority), re-reads identity/state, retries with bounded backoff, and records attempt scheduling transactionally. Crash before cleanup leaves pending work; crash after Status commit before completion causes safe repeat; worker/request contention serializes on the shared fence. No positive cache or process-local ownership is durable proof. No guarantee of eventual completion while either DB is unavailable, worker is disabled, or imports violate nonreuse; expose backlog/age metrics without PII. Lease state is unnecessary if the DB transaction fence covers each bounded attempt; never hold a long queue transaction over multiple intents.
